---
title: "Release process"
description: "Commit, version, verify, and publish Suchi releases."
---

Suchi uses Conventional Commits, Keep a Changelog, and SemVer. Pre-1.0
releases may break documented interfaces when that produces a cleaner product;
the changelog must still explain the impact.

## Commits

Use this shape:

```text
<type>(<scope>)!?: <short summary>

<brief explanation when needed>
```

Common types are `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`,
and `chore`. Scopes name the affected area, such as `mail`, `ui`, or `api`.
Use `!` and a `BREAKING CHANGE:` footer when a commit breaks a documented
interface.

Keep subjects brief and bodies focused.

## Changelog and versions

User-visible changes update the `[Unreleased]` section of
[`CHANGELOG.md`](https://github.com/johnnybravo-xyz/suchi/blob/main/CHANGELOG.md)
in the same pull request. Write for operators and call out required migration
steps directly.

Suchi follows SemVer:

- `MAJOR`: incompatible stable-interface changes after 1.0
- `MINOR`: features and potentially breaking pre-1.0 changes
- `PATCH`: fixes and internal changes

Only the current pre-1.0 release is supported.

## Release checklist

1. Move the `[Unreleased]` entries under the new version and date.
2. Confirm the shipped Microsoft OAuth client ID is registered and is not the
   sentinel value. The publishing workflow also enforces this gate.
3. Run the local verification suite:

   ```sh
   make check
   make smoke
   make bench-check
   docker build --check .
   docker compose config --quiet
   cd docs && npx mint@latest broken-links
   git diff --check
   ```

4. Manually exercise behavior that depends on external services or accounts,
   including Microsoft sign-in, configured email providers, and hosted LLMs
   affected by the release.
5. Recheck public size, memory, startup, network, and feature claims against
   the accepted benchmark and the final build.
6. Commit the release metadata, then create and push a signed annotated tag:

   ```sh
   git tag -s v0.1.0 -m "suchi 0.1.0"
   git push origin v0.1.0
   ```

7. Dispatch the manual release workflow:

   ```sh
   make release VERSION=v0.1.0
   ```

   Use `PUBLISH=false` for an artifacts-only run.

The workflow builds standard and full multi-architecture images, cross-platform
binaries, checksums, SBOMs, signatures, and GitHub release notes derived from
the changelog. Tag pushes alone do not publish anything.

## Automation

- `ci.yml` runs formatting, tests, vet, lint, schema, and UI checks.
- `smoke.yml` tests the built image and an ingest path.
- `restore-drill.yml` validates backup restoration.
- `release.yml` is manually dispatched from an existing tag.

For a security hotfix, branch from the affected tag, land the fix and changelog
entry, publish the patch release, then merge the fix back into `main`.
