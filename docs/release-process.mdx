Suchi uses Conventional Commits, Keep a Changelog, and SemVer. Pre-1.0
releases may break documented interfaces when that produces a cleaner product;
the changelog must still explain the impact.

## Commits

Use this shape:

```text
<type>(<scope>)!?: <short summary>

<brief explanation when needed>
```

Common types are `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`,
and `chore`. Scopes name the affected area, such as `mail`, `ui`, or `api`.
Use `!` and a `BREAKING CHANGE:` footer when a commit breaks a documented
interface.

Keep subjects brief and bodies focused.

## Repository and tag authority

GitHub `gh` hosts the release workflow, artifacts, images, and release notes. A
release is not ready to dispatch until the signed annotated tag resolves to the
same commit locally and on GitHub. Push the release commit and that exact tag;
never recreate a tag independently after pushing it.

## Changelog and versions

User-visible changes update the `[Unreleased]` section of
[`CHANGELOG.md`](https://github.com/johnnybravo-xyz/suchi/blob/main/CHANGELOG.md)
in the same pull request. Write for operators and call out required migration
steps directly.

A published core migration is immutable. A release normally adds at most one
numbered core migration; never rewrite or renumber one that shipped.

Suchi follows SemVer:

- `MAJOR`: incompatible stable-interface changes after 1.0
- `MINOR`: features and potentially breaking pre-1.0 changes
- `PATCH`: fixes and internal changes

Only the current pre-1.0 release is supported.

## Stable-v1 database compatibility

This section is the release authority for accepted core database states. The
signed pre-v0.1.0 SQL, tags and release artifacts remain byte-identical.
v0.1.0 embeds frozen compatibility SQL in
`core/db/compatibility/0002`–`0005`; its declarative baseline is active migration
`0001_baseline.sql`, `user_version = 1`, lineage `stable-v1`. v0.2.0 added
active migrations 0002–0003 and targets schema 3; v0.3.0 added 0004 and targets
schema 4; v0.4.0 added 0005 and targets schema 5; v0.5.0 added 0006 and targets
schema 6. v0.6.0 adds no core migration.

| 2 | Development boundary | `645e7798d663fff83d120182f661e7148fbd68d263517de9d44783d80aaebae3` |

| Pre-identity schema 4 | Exact pre-identity fingerprint above with `final-beta-schema-3` | Snapshot, apply frozen 0005 plus active 0002–0006, adopt stable lineage/schema 6 |
| Stable schema 1 | Exact schema-1 fingerprint above with `stable-v1` | Check integrity/foreign keys, apply active 0002–0006, require schema-6 manifest |
| Stable schema 2 | Exact schema-2 fingerprint above with `stable-v1` | Check integrity/foreign keys, apply active 0003–0006, require schema-6 manifest |
| Stable schema 3 | Exact schema-3 fingerprint above with `stable-v1` | Check integrity/foreign keys, apply active 0004–0006, require schema-6 manifest |
| Stable schema 4 | Exact schema-4 fingerprint above with `stable-v1` | Check integrity/foreign keys, apply active 0005–0006, require schema-6 manifest |
| Stable schema 5 | Exact schema-5 fingerprint above with `stable-v1` | Check integrity/foreign keys, apply active 0006, require schema-6 manifest |
| Stable schema 6 | Exact current fingerprint above with `stable-v1` | No-op |

“Canonical” means the complete normalized core `sqlite_schema` fingerprint, not
only the integer version or a claimed lineage row. Intermediate, partial,
spoofed, corrupt and future schemas are rejected before mutation and do not get
an adoption snapshot. Extension objects created after
`_suchi_extension_migrations` are outside the core fingerprint; core objects
rebuilt during adoption remain part of it regardless of their replacement
rowids.

Frozen compatibility migration 0005 rebuilds `users` and `audit_events` while
preserving numeric IDs and logical owner references. Active migration 0002 adds
version-family storage and validates predecessor graphs; 0004 adds title
ownership and its revision guard; 0005 adds sealed local-auth TOTP seeds and
digested recovery codes; 0006 adds watched-folder blocked state, rendered-path
claim keys and extraction diagnostics. All accepted paths reach the fresh
schema-6 fingerprint.

Every admitted pre-stable database passes integrity and foreign-key checks,
gets an exclusive mode-0600 SQLite snapshot beside the live database, and
applies the remaining compatibility steps, active migrations 0002–0006, stable
lineage and schema version 6 in one immediate writer transaction. Startup then
requires the fresh schema-6 manifest. Failure rolls back the transaction and
retains the snapshot. Fresh and already-current databases do not create
adoption snapshots. Stable-lineage forward upgrades also do not create one;
keep the operator's complete backup before upgrading.

Before release, verify fresh initialization and restart, all five pre-stable
paths, stable schema 1–5 forward upgrades, data and ID preservation, snapshot
creation and failure, fault-injected rollback, foreign-key restoration, cycle
rejection without a version bump, invalid-state rejection without writes, and
final manifest equality. Keep the operator's complete backup containing
SQLite, blobs, the credential key and configuration; an adoption snapshot is
database-only. See [Storage and transaction
invariants](/architecture-storage) and [Backup and
restore](/backup-restore#upgrade-and-rollback).

### Major-version schema epochs

Suchi resets migration history at major releases instead of carrying every old
upgrade path forever:

1. The final release of the outgoing major is the bridge. It accepts the last
   canonical schema, applies one reviewed conversion, and writes an
   application-owned marker such as `schema_state(epoch, version)`.
2. The new major starts from one declarative baseline. Fresh installs create it
   directly; the normal runtime drops older migrations, fingerprints, and
   release-specific checksums. Git tags retain that history.
3. Migrations within the new major use the application-owned epoch/version
   marker rather than `PRAGMA user_version`. Some explicit compatibility marker
   remains mandatory so partial or hand-edited databases fail closed.
4. Older databases upgrade through the bridge release. If direct legacy
   conversion becomes necessary, it belongs in a separate offline upgrade
   command, not normal server startup.
5. Repeat only at the next major boundary: v1 carries v1 migrations, v2 starts
   a new epoch, and so on.

The first cutover is v1.0. Until its bridge ships, the pre-1.0 compatibility
table above remains authoritative.

### Already-adopted pre-identity archives

An untagged archive may already carry `user_version = 1` and `stable-v1` while
still matching the pre-identity fingerprint. Automatic startup deliberately
rejects that state: it has crossed the old adoption boundary and does not have a
new automatic pre-adoption snapshot.

Use only the reviewed manual path:

1. Preserve a live browser session before the window if an existing OIDC
   account must be bound; verified-email fallback is intentionally absent.
2. Stop Suchi and every CLI/import writer. Require the exact pre-identity
   fingerprint, valid lineage/version, clean integrity and foreign keys, and the
   reviewed 0005 checksum before changing the database.
3. Copy the complete quiescent data directory and effective configuration to
   verified storage outside `DATA_DIR`; keep the old binary/config. A normal
   live database copy is not rollback.
4. Apply the exact 0005 SQL through the table-rebuild transaction, restore
   `user_version = 1` and `stable-v1`, then require the exact stable schema-1
   fingerprint, integrity, foreign keys, stable user IDs, and expected counts
   before starting any writer.
5. Start the current binary. It admits that exact schema-1 state, applies active
   migrations 0002–0006, and requires the schema-6 manifest. From the preserved
   session, use **Sync from identity provider** and verify the same user ID gains
   issuer/subject, a retained `user.oidc_bound` row, a replacement cookie, and
   unchanged ownership.

When adopting a pre-v0.1.0 archive, keep both the automatic database snapshot and a complete
operator backup. If no live session survives to bind an occupied unbound OIDC
email, stop and restore with the old binary/config; do not delete, merge, or
recreate the account to bypass the conflict.

## Release checklist

Suchi Companion has an independent version and signed tag. Its release gates,
artifact checks and coordinated store publication order live in the
[Companion release runbook](https://github.com/johnnybravo-xyz/suchi-companion/blob/main/RELEASE.md);
do not duplicate them here.

1. Build and verify the web app from the release sources:

   ```sh
   make ui-check
   make ui-verify
   ```

   `core/ui/spa/dist` remains ignored. CI builds it once from the immutable
   release revision, passes that artifact to every tagged binary build, and
   rebuilds it in the pinned Bun stage for container images.

2. Move the `[Unreleased]` entries under the new version and date. Update
   `developmentVersion` in `distro/cmd/suchi/main.go` to the current source version
   line with a `-dev` suffix.
3. Review every OCR, content and LLM pipeline revision changed since the previous
   release. `distro/cmd/suchi/pipeline_proposals.go` is the tagged automatic
   reminder policy:

   - Keep `0` when that pipeline has no recommended automatic upgrade.
   - Set a field to the current pipeline revision when existing successful
     results should receive a **Processing update** reminder.
   - Leave an earlier positive recommendation unchanged when a newer processing
     change is not worth prompting. This preserves the earlier recommendation
     for archives that skipped releases without opting in the newer revision.

   Each field is independent and cannot exceed its compiled pipeline revision.
   Commit this file with the release metadata; never inject or override the
   policy in the build workflow.

4. Confirm the shipped Microsoft OAuth registration still permits personal and
   work/school device-code sign-in.
5. Run the local verification suite:

   ```sh
   make check
   make security-check
   make smoke
   make bench-check
   docker build --check .
   docker compose config --quiet
   make docs-check
   git diff --check
   ```

6. Manually exercise behavior that depends on external services or accounts,
   including Microsoft sign-in, configured email providers, and hosted LLMs
   affected by the release.
7. Recheck public size, memory, startup, network, and feature claims against
   the accepted benchmark and the final build.
8. Commit the release metadata on `main`, create a signed annotated tag, and push
   the exact commit and tag to GitHub:

   ```sh
   export VERSION=v0.6.0
   git tag -s "$VERSION" -m "suchi ${VERSION#v}"
   ./hack/verify-release-tag.sh "$VERSION"
   git push gh main
   git push gh "refs/tags/$VERSION"
   ```

9. Dispatch the validation-only release workflow:

   ```sh
   make release VERSION="$VERSION"
   ```

   This verifies that the local and GitHub tags resolve to the same commit and
   runs the release gates without packaging or publishing artifacts. The release
   race suite starts alongside the reusable quality jobs. Publication waits for
   both it and preflight; preflight runs the tag, security, binary smoke,
   benchmark, container, and documentation checks after the reusable jobs pass.
   Do not set `PUBLISH=true` for v0.6.0. The checked-in proposal policy is
   identical across every published binary and image; zero thresholds preserve
   existing reminders, and explicit rescans remain available.
10. Build the cross-platform binaries, standalone AnyDoc archives, standard and
    full multi-architecture images, SBOMs and checksum manifests on `devlab`
    using the commands below. Sign the manifests on the release Mac, publish the
    GitHub release, then promote the moving image channels.

Release builds inject the version and source revision into the Go binary.
Settings reads the identity from `/api/whoami`, showing only the version for
tagged production releases. Unversioned builds use the source's
`developmentVersion` and append the short revision
when available. `suchi version` likewise retains an injected release version and
adds the revision for development builds. Docker has no `.git` directory, so
manual builds must pass `REVISION` to retain source identification and `VERSION`
for a tagged release. Local VCS builds without an injected version use the source
version line, not Go's tag-derived module pseudo-version. Missing development
revisions are labeled unavailable, not guessed.

## Building release assets without Actions

GHCR images can be built and pushed directly when Actions is unavailable. Build
from the release tag, never from a different branch with the release version
injected: the image contents must agree with the Git tag.

The Dockerfile pins base-image digests, the AnyDoc source commit and checked
third-party archives. Go and Cargo dependency checksums verify downloaded source.
Alpine and Debian runtime packages still resolve from their live repositories,
so these controls provide traceable inputs, not byte-for-byte reproducibility
from a source tag. The signed published image digest and its provenance/SBOM are
the release artifacts to verify and deploy.

Set the release coordinates on every build machine:

```sh
export VERSION=v0.6.0
export IMAGE=ghcr.io/johnnybravo-xyz/suchi
export CACHE_AMD64="$IMAGE:buildcache-amd64"
export CACHE_ARM64="$IMAGE:buildcache-arm64"
```

Check out that exact tag in a detached worktree or fresh clone:

```sh
git worktree add --detach "/tmp/suchi-$VERSION" "$VERSION"
cd "/tmp/suchi-$VERSION"
```

Authenticate with a classic GitHub personal access token carrying
`write:packages`. The login username is the personal account that owns the
token, which may differ from the organization in `IMAGE`:

```sh
printf '%s' "$CR_PAT" |
  docker login ghcr.io -u "$GITHUB_USER" --password-stdin
unset CR_PAT
```

### Build all release assets on devlab

The v0.6.0 release uses the Debian 13 x86-64 `devlab` host, not GitHub Actions.
The host needs Go 1.27.4, Bun 1.4.4, Docker Buildx with QEMU support, and Syft
1.51.0. It holds no release signing key.

From the detached signed tag, bind every output to that exact revision:

```sh
export REVISION="$(git rev-parse "$VERSION^{commit}")"
test "$(git rev-parse HEAD)" = "$REVISION"
./hack/verify-release-tag.sh "$VERSION"

make ui
go run ./hack/ui-assets verify ui core/ui/spa/dist
rm -rf dist/release /tmp/suchi-anydoc
mkdir -p dist/release /tmp/suchi-anydoc/context
```

Build the static Suchi binary matrix:

```sh
for target in linux/amd64 linux/arm64 darwin/amd64 darwin/arm64 windows/amd64; do
  goos=${target%/*}
  goarch=${target#*/}
  bin="suchi-${VERSION}-${goos}-${goarch}"
  test "$goos" = windows && bin="${bin}.exe"
  CGO_ENABLED=0 GOOS="$goos" GOARCH="$goarch" go build \
    -tags=embedded_ui \
    -trimpath \
    -ldflags="-s -w -X main.version=${VERSION} -X main.revision=${REVISION}" \
    -o "dist/release/$bin" ./distro/cmd/suchi
done
```

Export and package the pinned AnyDoc binary for both Linux architectures. The
same verified exports become the named image build context, so the image builds
do not compile a second copy:

```sh
ANYDOC_TAG=$(awk -F= '$1 == "ARG ANYDOC_TAG" { print $2; exit }' Dockerfile)
ANYDOC_COMMIT=$(awk -F= '$1 == "ARG ANYDOC_COMMIT" { print $2; exit }' Dockerfile)

for arch in amd64 arm64; do
  out="/tmp/suchi-anydoc/export-${arch}"
  bundle="anydoc-${VERSION}-linux-${arch}"
  docker buildx build \
    --platform "linux/$arch" \
    --target anydoc \
    --output "type=local,dest=$out" .
  test -x "$out/$arch/anydoc"
  test -s "$out/$arch/LICENSE"

  mkdir -p "/tmp/suchi-anydoc/context/$arch" "dist/release/$bundle"
  cp "$out/$arch/anydoc" "$out/$arch/LICENSE" "/tmp/suchi-anydoc/context/$arch/"
  cp "$out/$arch/anydoc" "$out/$arch/LICENSE" "dist/release/$bundle/"
  printf '%s\n%s\n' \
    "This anydoc build is redistributed from firecrawl/anydoc" \
    "${ANYDOC_TAG} (${ANYDOC_COMMIT}) under the MIT license. Source: https://github.com/firecrawl/anydoc" \
    > "dist/release/$bundle/NOTICE"
  (cd dist/release && tar -czf "${bundle}.tar.gz" "$bundle")
  rm -rf "dist/release/$bundle"
done
```

Build and push only the immutable versioned standard and full image manifests:

```sh
for target in standard full; do
  suffix=
  test "$target" = full && suffix=-full
  docker buildx build \
    --file Dockerfile \
    --target "$target" \
    --platform linux/amd64,linux/arm64 \
    --build-context anydoc=/tmp/suchi-anydoc/context \
    --build-arg VERSION="$VERSION" \
    --build-arg REVISION="$REVISION" \
    --tag "$IMAGE:${VERSION}${suffix}" \
    --label org.opencontainers.image.source=https://github.com/johnnybravo-xyz/suchi \
    --label org.opencontainers.image.version="$VERSION" \
    --label org.opencontainers.image.licenses=AGPL-3.0 \
    --provenance=mode=max \
    --sbom=true \
    --push .
done
```

Record image digests, generate both SBOM formats, extract the release notes, and
checksum every downloadable binary, archive and SBOM:

```sh
: > dist/release/IMAGE_DIGESTS
for ref in "$IMAGE:$VERSION" "$IMAGE:$VERSION-full"; do
  docker buildx imagetools inspect "$ref" |
    awk -v ref="$ref" '$1 == "Digest:" { print $2 "  " ref; exit }' \
    >> dist/release/IMAGE_DIGESTS
done

syft "$IMAGE:$VERSION" -o spdx-json --file dist/release/suchi-standard.spdx.json
syft "$IMAGE:$VERSION" -o cyclonedx-json --file dist/release/suchi-standard.cyclonedx.json
syft "$IMAGE:$VERSION-full" -o spdx-json --file dist/release/suchi-full.spdx.json
syft "$IMAGE:$VERSION-full" -o cyclonedx-json --file dist/release/suchi-full.cyclonedx.json

awk -v h="## [${VERSION#v}]" '
  $0 == h || index($0, h " - ") == 1 { flag=1; next }
  flag && /^## \[/ { exit }
  flag { print }
' CHANGELOG.md > dist/release/notes.md

(cd dist/release && sha256sum suchi-* anydoc-*.tar.gz | sort > SHA256SUMS)
(cd dist/release && sha256sum -c SHA256SUMS)
```

Transfer `dist/release` to the release Mac without adding signing material to
`devlab`. Sign both manifests with the same release key whose public half ships
at `.github/release-signing-key.asc`:

```sh
cd dist/release
export RELEASE_KEY=D0B0F9E868440860B543E2A7D8C255808C9A0D9C # gitleaks:allow
gpg --local-user "$RELEASE_KEY" --armor --detach-sign \
  --output SHA256SUMS.asc SHA256SUMS
gpg --local-user "$RELEASE_KEY" --armor --detach-sign \
  --output IMAGE_DIGESTS.asc IMAGE_DIGESTS

gpg --verify SHA256SUMS.asc SHA256SUMS
gpg --verify IMAGE_DIGESTS.asc IMAGE_DIGESTS
shasum -a 256 -c SHA256SUMS
```

Publish those exact files, then promote channels only after the release exists:

```sh
gh release create "$VERSION" \
  suchi-* anydoc-*.tar.gz \
  SHA256SUMS SHA256SUMS.asc IMAGE_DIGESTS IMAGE_DIGESTS.asc \
  --verify-tag \
  --title "suchi $VERSION" \
  --notes-file notes.md

docker buildx imagetools create --tag "$IMAGE:latest" "$IMAGE:$VERSION"
docker buildx imagetools create --tag "$IMAGE:latest-full" "$IMAGE:$VERSION-full"
```

Downloaded assets verify against the checked-in public key and the signed
checksum manifest:

```sh
gpg --import .github/release-signing-key.asc
gpg --verify SHA256SUMS.asc SHA256SUMS
sha256sum -c SHA256SUMS
```

The signed `IMAGE_DIGESTS` file is the trust anchor for the devlab-built image
manifests; GitHub Actions OIDC identities do not apply to these images.

### Alternative: build on native architecture hosts

When QEMU makes the AnyDoc build impractical, build each architecture on a
native host. Check out the same signed tag and authenticate to GHCR on both.
Set these host-specific values:

```sh
# x86-64 Linux host
export PLATFORM=linux/amd64 ARCH=amd64 CACHE="$CACHE_AMD64"

# Apple Silicon or Linux ARM64 host
export PLATFORM=linux/arm64 ARCH=arm64 CACHE="$CACHE_ARM64"
```

On each host, publish both architecture-specific images:

```sh
for target in standard full; do
  suffix=
  test "$target" = full && suffix=-full
  docker buildx build \
    --file Dockerfile \
    --target "$target" \
    --platform "$PLATFORM" \
    --build-arg VERSION="$VERSION" \
    --build-arg REVISION="$(git rev-parse HEAD)" \
    --tag "$IMAGE:$VERSION$suffix-$ARCH" \
    --label org.opencontainers.image.source=https://github.com/johnnybravo-xyz/suchi \
    --label org.opencontainers.image.version="$VERSION" \
    --label org.opencontainers.image.licenses=AGPL-3.0 \
    --cache-from type=registry,ref="$CACHE" \
    --cache-to type=registry,ref="$CACHE",mode=max \
    --provenance=mode=max \
    --sbom=true \
    --push .
done
```

After both hosts finish, create and verify only the immutable version manifests:

```sh
for target in standard full; do
  suffix=
  test "$target" = full && suffix=-full
  docker buildx imagetools create \
    --tag "$IMAGE:$VERSION$suffix" \
    "$IMAGE:$VERSION$suffix-amd64" \
    "$IMAGE:$VERSION$suffix-arm64"
  docker buildx imagetools inspect "$IMAGE:$VERSION$suffix"
  docker pull --platform linux/amd64 "$IMAGE:$VERSION$suffix"
  docker pull --platform linux/arm64 "$IMAGE:$VERSION$suffix"
done
```

Then resume the signing, GitHub Release and channel-promotion steps above.
Never promote a moving alias in the command that first publishes a version
manifest. The first command-line push may create a private, unlinked GHCR
package; make it public and connect it to this repository.

## Automation

- `checks.yml` runs the complete repository validation graph on pushes to
  `main`, pull requests and manual dispatch.
- `ci.yml` runs formatting, tests, vet, lint, documentation release-metadata
  checks, UI checks and browser tests when called by it.
- `smoke.yml` tests the built images and ingest paths when called by it.
  Both variants are rebuilt with the exported AnyDoc context and an unusable
  Rust base to catch accidental recompilation; binary and license bytes must
  match the export before the usual ingestion checks run.
- `restore-drill.yml` validates backup restoration when called by it.
- `release.yml` defaults to validation-only when manually dispatched from an
  existing signed annotated tag. Its preflight repeats the complete reusable
  validation graph, race tests, security scans, local smoke and benchmark
  gates, Docker checks and documentation validation. `publish=true` retains
  the legacy Actions publication graph but is not used for v0.6.0.

The release workflow verifies the tag with the public key pinned at
`.github/release-signing-key.asc` and the expected full fingerprint in
`hack/verify-release-tag.sh`. It rejects missing, lightweight, unsigned,
wrong-key, locally divergent and remotely divergent tags. Validation-only runs
skip release notes, binary and image packaging, artifact collection, GitHub
Release creation and channel promotion. Reusable checks may carry their
short-lived SPA build between jobs; it is not a release artifact.

For a security hotfix, branch from the affected tag, land the fix and changelog
entry, publish the patch release, then merge the fix back into `main`.
