Suchi uses Conventional Commits, Keep a Changelog, and SemVer. Pre-1.0
releases may break documented interfaces when that produces a cleaner product;
the changelog must still explain the impact.

## Commits

Use this shape:

```text
<type>(<scope>)!?: <short summary>

<brief explanation when needed>
```

Common types are `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`,
and `chore`. Scopes name the affected area, such as `mail`, `ui`, or `api`.
Use `!` and a `BREAKING CHANGE:` footer when a commit breaks a documented
interface.

Keep subjects brief and bodies focused.

## Repository and tag authority

GitHub `gh` hosts the release workflow, artifacts, images, and release notes. A
release is not ready to dispatch until the signed annotated tag resolves to the
same commit locally and on GitHub. Push the release commit and that exact tag;
never recreate a tag independently after pushing it.

## Changelog and versions

User-visible changes update the `[Unreleased]` section of
[`CHANGELOG.md`](https://github.com/johnnybravo-xyz/suchi/blob/main/CHANGELOG.md)
in the same pull request. Write for operators and call out required migration
steps directly.

A published core migration is immutable. A release normally adds at most one
numbered core migration; never rewrite or renumber one that shipped.

Suchi follows SemVer:

- `MAJOR`: incompatible stable-interface changes after 1.0
- `MINOR`: features and potentially breaking pre-1.0 changes
- `PATCH`: fixes and internal changes

Only the current pre-1.0 release is supported.

## Stable-v1 database compatibility

This section is the release authority for accepted core database states. The
signed beta.1–beta.3 SQL, tags and release artifacts remain byte-identical.
Stable v0.1.0 embeds frozen compatibility SQL in
`core/db/compatibility/0002`–`0005`; the active catalog still contains only the
declarative `0001_baseline.sql` and identifies the stable epoch as
`user_version = 1`, lineage `stable-v1`.

The final stable-v1 normalized core fingerprint is
`9d2a6320eae1582b0f294caa6ed518b5a73ab3dbe6597c9ca1a36cc563e03240`.
The one admitted pre-identity schema-4 boundary is
`5d6ac98308eb644b030092178792a46f36e6f8f5041411f020ed2dcf216f46c2`.
Startup admits only these exact states:

| Source database | Required identity | Stable-v1 startup action |
| --- | --- | --- |
| Empty | `user_version = 0`, no core objects or lineage | Apply the declarative baseline |
| v0.1.0-beta.1 | Canonical beta.1 schema 1, no lineage table | Snapshot, apply frozen 0002–0005, adopt stable lineage |
| v0.1.0-beta.2 | Canonical beta.2 schema 2, no lineage table | Snapshot, apply frozen 0003–0005, adopt stable lineage |
| v0.1.0-beta.3 | Canonical schema 3 with `final-beta-schema-3` | Snapshot, apply frozen 0004–0005, adopt stable lineage |
| Historical schema 3 | Known pre-beta mutable-baseline fingerprint with `final-beta-schema-3`; obsolete `agent_webhooks` table must be empty | Snapshot, remove the empty obsolete table, apply 0004–0005, adopt stable lineage |
| Pre-identity schema 4 | Exact pre-identity fingerprint above with `final-beta-schema-3` | Snapshot, apply 0005, adopt stable lineage |
| Stable v1 | Exact final fingerprint above with `stable-v1` | No-op |

“Canonical” means the complete normalized core `sqlite_schema` fingerprint, not
only the integer version or a claimed lineage row. Intermediate, partial,
spoofed, corrupt and future schemas are rejected before mutation and do not get
an adoption snapshot. Extension objects created after
`_suchi_extension_migrations` are outside the core fingerprint; core objects
rebuilt during adoption remain part of it regardless of their replacement
rowids.

Compatibility migration 0005 rebuilds `users` with nullable issuer/subject and
rebuilds `audit_events` with retained-event metadata. It copies numeric user and
audit IDs exactly, so foreign-key and logical owner references stay stable.
All accepted pre-stable paths reach the same fresh-schema fingerprint.

Every admitted pre-stable database passes integrity and foreign-key checks, gets
an exclusive mode-0600 SQLite snapshot beside the live database, and applies
the remaining compatibility steps, stable lineage and stable version in one
immediate writer transaction. Startup then checks integrity, foreign keys and
equality with the fresh stable schema manifest. Failure rolls back the
transaction and retains the snapshot. Fresh and already-stable databases do not
create adoption snapshots.

Before release, verify fresh initialization and restart, all five pre-stable
paths, data/ID preservation, snapshot creation and failure, fault-injected
rollback, foreign-key restoration, invalid-state rejection without writes, and
final manifest equality. Keep the operator's complete backup containing SQLite,
blobs, the credential key and configuration; the adoption snapshot is
database-only. See [Architecture](/architecture#storage-and-transaction-invariants)
for runtime invariants and [Backup and restore](/backup-restore#upgrade-and-rollback)
for operator procedure.

### Already-adopted pre-identity archives

An untagged archive may already carry `user_version = 1` and `stable-v1` while
still matching the pre-identity fingerprint. Automatic startup deliberately
rejects that state: it has crossed the old adoption boundary and does not have a
new automatic pre-adoption snapshot.

Use only the reviewed manual path:

1. Preserve a live browser session before the window if an existing OIDC
   account must be bound; verified-email fallback is intentionally absent.
2. Stop Suchi and every CLI/import writer. Require the exact pre-identity
   fingerprint, valid lineage/version, clean integrity and foreign keys, and the
   reviewed 0005 checksum before changing the database.
3. Copy the complete quiescent data directory and effective configuration to
   verified storage outside `DATA_DIR`; keep the old binary/config. A normal
   live database copy is not rollback.
4. Apply the exact 0005 SQL through the table-rebuild transaction, restore
   `user_version = 1` and `stable-v1`, then require the final fingerprint,
   integrity, foreign keys, stable user IDs, and expected counts before starting
   any writer.
5. Start the final binary. From the preserved session, use **Sync from identity
   provider** and verify the same user ID gains issuer/subject, a retained
   `user.oidc_bound` row, a replacement cookie, and unchanged ownership.

For beta adoption, keep both the automatic database snapshot and a complete
operator backup. If no live session survives to bind an occupied unbound OIDC
email, stop and restore with the old binary/config; do not delete, merge, or
recreate the account to bypass the conflict.

The standalone [beta archive upgrade runbook](https://github.com/johnnybravo-xyz/suchi/blob/main/BETA-UPGRADE.md)
expands this into hard-gated, agent-executable rehearsal, cutover, identity
binding, evidence, and rollback commands.

## Release checklist

Suchi Companion has an independent version and signed tag. Its release gates,
artifact checks and coordinated store publication order live in the
[Companion release runbook](https://github.com/johnnybravo-xyz/suchi-companion/blob/main/RELEASE.md);
do not duplicate them here.

1. When the web app changed, rebuild its committed embedded copy and review the
   generated asset changes:

   ```sh
   make ui
   git diff -- core/ui/spa/dist
   ```

2. Move the `[Unreleased]` entries under the new version and date. Update
   `developmentVersion` in `distro/cmd/suchi/main.go` to the current source version
   line with a `-dev` suffix.
3. Review every OCR, content and LLM pipeline revision changed since the previous
   release. `distro/cmd/suchi/pipeline_proposals.go` is the tagged automatic
   reminder policy:

   - Keep `0` when that pipeline has no recommended automatic upgrade.
   - Set a field to the current pipeline revision when existing successful
     results should receive a **Processing update** reminder.
   - Leave an earlier positive recommendation unchanged when a newer processing
     change is not worth prompting. This preserves the earlier recommendation
     for archives that skipped releases without opting in the newer revision.

   Each field is independent and cannot exceed its compiled pipeline revision.
   Commit this file with the release metadata; never inject or override the
   policy in the build workflow.

4. Confirm the shipped Microsoft OAuth registration still permits personal and
   work/school device-code sign-in.
5. Run the local verification suite:

   ```sh
   make check
   make security-check
   make smoke
   make bench-check
   docker build --check .
   docker compose config --quiet
   make docs-check
   git diff --check
   ```

6. Manually exercise behavior that depends on external services or accounts,
   including Microsoft sign-in, configured email providers, and hosted LLMs
   affected by the release.
7. Recheck public size, memory, startup, network, and feature claims against
   the accepted benchmark and the final build.
8. Commit the release metadata on `main`, create a signed annotated tag, and push
   the exact commit and tag to GitHub:

   ```sh
   export VERSION=v0.1.0
   git tag -s "$VERSION" -m "suchi ${VERSION#v}"
   ./hack/verify-release-tag.sh "$VERSION"
   git push gh main
   git push gh "refs/tags/$VERSION"
   ```

9. Dispatch the manual release workflow:

   ```sh
   make release VERSION="$VERSION"
   ```

   This verifies that the local and GitHub tags resolve to the same commit. Use
   `PUBLISH=false` for an artifacts-only run. The checked-in proposal policy is
   identical across every binary and image built from the tag. Zero thresholds
   do not cancel existing reminders, and explicit rescans remain available.

The workflow builds standard and full multi-architecture images, cross-platform
binaries, checksums, SBOMs, signatures, and GitHub release notes derived from
the changelog. Tag pushes alone do not publish anything.

Release notes travel as a workflow artifact into the collector, rather than a
multiline job output that GitHub's secret detection may silently suppress.

AnyDoc is compiled once per Linux architecture through the Dockerfile's
`anydoc` export target. Those binaries and licenses are packaged for standalone
downloads. The image job downloads only that run's AnyDoc artifacts, verifies
their checksums, and supplies them as an `anydoc` named build context for both
runtime variants. Docker selects the matching `amd64` or `arm64` directory;
missing or damaged artifacts fail the build instead of triggering recompilation.
Plain local Docker builds omit that context and still compile from pinned source.

Release builds inject the version and source revision into the Go binary.
Settings reads the identity from `/api/whoami`, showing only the version for
tagged production releases. Unversioned builds use the source's
`developmentVersion` and append the short revision
when available. `suchi version` likewise retains an injected release version and
adds the revision for development builds. Docker has no `.git` directory, so
manual builds must pass `REVISION` to retain source identification and `VERSION`
for a tagged release. Local VCS builds without an injected version use the source
version line, not Go's tag-derived module pseudo-version. Missing development
revisions are labeled unavailable, not guessed.

## Publishing container images without Actions

GHCR images can be built and pushed directly when Actions is unavailable. Build
from the release tag, never from a different branch with the release version
injected: the image contents must agree with the Git tag.

The Dockerfile pins base-image digests, the AnyDoc source commit and checked
third-party archives. Go and Cargo dependency checksums verify downloaded source.
Alpine and Debian runtime packages still resolve from their live repositories,
so these controls provide traceable inputs, not byte-for-byte reproducibility
from a source tag. The signed published image digest and its provenance/SBOM are
the release artifacts to verify and deploy.

Set the release coordinates on every build machine:

```sh
export VERSION=v0.1.0
export IMAGE=ghcr.io/johnnybravo-xyz/suchi
export CACHE_AMD64="$IMAGE:buildcache-amd64"
export CACHE_ARM64="$IMAGE:buildcache-arm64"
```

Check out that exact tag in a detached worktree or fresh clone:

```sh
git worktree add --detach "/tmp/suchi-$VERSION" "$VERSION"
cd "/tmp/suchi-$VERSION"
```

Authenticate with a classic GitHub personal access token carrying
`write:packages`. The login username is the personal account that owns the
token, which may differ from the organization in `IMAGE`:

```sh
printf '%s' "$CR_PAT" |
  docker login ghcr.io -u "$GITHUB_USER" --password-stdin
unset CR_PAT
```

### Build on native architecture hosts

Rust compilation for `anydoc` is very slow through QEMU. A cancelled
`cargo build` step is not cached because its Docker layer never completes. For
a faster multi-architecture release, build AMD64 on an x86-64 Linux host and
ARM64 on an Apple Silicon or Linux ARM64 host, push temporary architecture
tags, and combine them into the public manifest.

On the x86-64 Linux host:

```sh
docker buildx build \
  --file Dockerfile \
  --target standard \
  --platform linux/amd64 \
  --build-arg VERSION="$VERSION" \
  --build-arg REVISION="$(git rev-parse HEAD)" \
  --tag "$IMAGE:$VERSION-amd64" \
  --label org.opencontainers.image.source=https://github.com/johnnybravo-xyz/suchi \
  --label org.opencontainers.image.version="$VERSION" \
  --label org.opencontainers.image.licenses=AGPL-3.0 \
  --cache-from type=registry,ref="$CACHE_AMD64" \
  --cache-to type=registry,ref="$CACHE_AMD64",mode=max \
  --provenance=mode=max \
  --sbom=true \
  --push .
```

On the native ARM64 host, after checking out the same tag and logging into
GHCR:

```sh
docker buildx build \
  --file Dockerfile \
  --target standard \
  --platform linux/arm64 \
  --build-arg VERSION="$VERSION" \
  --build-arg REVISION="$(git rev-parse HEAD)" \
  --tag "$IMAGE:$VERSION-arm64" \
  --label org.opencontainers.image.source=https://github.com/johnnybravo-xyz/suchi \
  --label org.opencontainers.image.version="$VERSION" \
  --label org.opencontainers.image.licenses=AGPL-3.0 \
  --cache-from type=registry,ref="$CACHE_ARM64" \
  --cache-to type=registry,ref="$CACHE_ARM64",mode=max \
  --provenance=mode=max \
  --sbom=true \
  --push .
```

After both builds are present in GHCR, create only the versioned manifest:

```sh
docker buildx imagetools create \
  --tag "$IMAGE:$VERSION" \
  "$IMAGE:$VERSION-amd64" \
  "$IMAGE:$VERSION-arm64"
```

Confirm that both platform manifests are available:

```sh
docker buildx imagetools inspect "$IMAGE:$VERSION"
docker pull --platform linux/amd64 "$IMAGE:$VERSION"
docker pull --platform linux/arm64 "$IMAGE:$VERSION"
```

Build and verify the full image the same way under `$IMAGE:$VERSION-full`.
Complete image signing, checksums, SBOMs, release artifacts, and the GitHub
Release before changing a moving channel. Only then promote the stable versioned
manifests:

```sh
docker buildx imagetools create \
  --tag "$IMAGE:latest" \
  "$IMAGE:$VERSION"
docker buildx imagetools create \
  --tag "$IMAGE:latest-full" \
  "$IMAGE:$VERSION-full"
```

Release candidates promote `rc` / `rc-full`; beta releases promote `beta` /
`beta-standard` and `beta-full`. Never create a moving alias in the same command
that first publishes the version manifest.

The first successful native build seeds its architecture's registry cache.
Later local releases import those caches, while the release workflow imports
both native caches for runtime layers and maintains its own GitHub Actions cache.
Release images obtain AnyDoc from the standalone artifacts described above.
For local source builds, the `anydoc` source commit and build instructions are
pinned independently of the Suchi version, so the completed Rust layer is reused
until that pin or recipe changes. Cargo registry and target cache mounts also
retain incremental work in the local BuildKit builder when a compile is
interrupted before its image layer can be exported.

The `full` image uses `--target full` and temporary tags ending in
`-full-amd64` and `-full-arm64`.

The first command-line push creates a private, unlinked GHCR package by
default. In the package settings, make it public, connect it to the Suchi
repository, and grant that repository Actions access so later workflow pushes
can update it. Direct local publication does not reproduce the workflow's
keyless Cosign signatures or GitHub release artifacts; handle those separately
before calling the release complete.

## Automation

- `checks.yml` runs the complete repository validation graph on pushes to
  `main`, pull requests and manual dispatch.
- `ci.yml` runs formatting, tests, vet, lint, documentation release-metadata
  checks, UI checks and browser tests when called by it.
- `smoke.yml` tests the built images and ingest paths when called by it.
  Both variants are rebuilt with the exported AnyDoc context and an unusable
  Rust base to catch accidental recompilation; binary and license bytes must
  match the export before the usual ingestion checks run.
- `restore-drill.yml` validates backup restoration when called by it.
- `release.yml` publishes only when manually dispatched from an existing signed
  annotated tag. Its preflight repeats the complete reusable validation graph,
  race tests, security scans, local smoke and benchmark gates, Docker checks and
  documentation validation. Only jobs that publish releases, packages or
  keyless signatures receive the corresponding write permissions.

The release workflow verifies the tag with the public key pinned at
`.github/release-signing-key.asc` and the expected full fingerprint in
`hack/verify-release-tag.sh`. It rejects missing, lightweight, unsigned,
wrong-key, locally divergent and remotely divergent tags.

Images wait for both binary matrices before publication and reuse the AnyDoc
matrix's verified binaries rather than rebuilding them. Release runs are
serialized because moving image channels are shared mutable state.
Artifacts-only branch runs use `snapshot-<commit>` names and skip signing and
publication; they still produce ordinary workflow artifacts and GHA caches.

For a security hotfix, branch from the affected tag, land the fix and changelog
entry, publish the patch release, then merge the fix back into `main`.
