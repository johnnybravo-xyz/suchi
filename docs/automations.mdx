---
title: "Automations"
description: "Deterministic filing with typed triggers and ordered metadata actions."
---

Automations are Suchi's filing layer. Each automation combines one or more event
filters with an ordered action list, lives in SQLite, and can be managed in the
Automations screen or through the API. Ordinary rules are deterministic; an
optional **Ask the classifier** branch maps one bounded model answer onto
administrator-configured local actions. Human decisions belong in
[Approvals](/approvals).

Rules and their vocabulary belong to one [filing system](/jd). Matching, offered
categories, symbolic names and runtime metadata IDs stay in the document's system;
equal names/codes in S01 and S02 do not collide. Category assignment cannot transfer
a document. Owner assignment requires an active member/admin of that system.
Actorless custom-field document-link actions may target only live same-system
documents; authenticated API links require separate source/target authorization.
Disabled originals and edited forks survive reimport independently in each system.

## Triggers

| Trigger            | Timing                                              |
| ------------------ | --------------------------------------------------- |
| `consumption`      | When source context is available, before extraction |
| `document_added`   | After extraction and local archive matching         |
| `document_updated` | After an explicit metadata update                   |

Triggers can filter by source path, filename, mail rule, tag, correspondent,
title or content regex, sender, subject, mailbox folder, and attachment
presence. Multiple filters on one trigger use AND. Multiple triggers on an
automation use OR.

## Actions

The visual builder exposes title, tag, correspondent, Johnny.Decimal category,
folder-layout, owner, and custom-field assignment. Folder layouts, eligible
owners, and custom fields use named pickers; the value editor follows the
selected custom field's declared type. The API continues to persist their IDs.
A layout that uses the previous archive number fails atomically for a document
without that compatibility value.

The screen keeps custom rules in the main centered list and places filing-tree
rules in a separate collapsed **Built-in automations** section below it. The JSON
view remains available for inspecting the complete automation.

The server exposes the current builder vocabulary and parameter schemas at
`GET /api/automations/schema`. Actions run in order inside one transaction;
failure rolls back that automation and is recorded in structured logs. Trigger
types and glob or regular-expression filters are validated when a rule is
saved, so malformed rules do not silently sit idle.
Automations do not re-trigger themselves from their own writes, so dependent
actions should stay in one automation.

Assignment and removal actions are designed to converge when retried.
`discard` is idempotent for an already-trashed document and retains its original
Trash timestamp. Other metadata actions still require a live document; discarding
does not grant a rule permission to edit Trash or cross a filing-system boundary.

Example:

```json
{
  "name": "Acme invoices",
  "order": 20,
  "enabled": true,
  "triggers": [
    {
      "type": 2,
      "filter_has_correspondent": 12,
      "filter_content_matching": "invoice|bill"
    }
  ],
  "actions": [
    { "type": "assign_tags", "params": { "tag_ids": [7] } },
    {
      "type": "assign_title",
      "params": { "template": "Acme invoice {{date}}" }
    }
  ]
}
```

Title templates support `{{title}}`, `{{correspondent}}`, `{{tags}}`, and
`{{date}}`. Unknown placeholders remain visible so a typo does not silently
erase text. The visual builder resolves names to IDs; direct JSON action
parameters continue to use IDs.

## Ask the classifier

An administrator can attach one closed question to a `document_added`
automation. The Automations builder supports **Yes / No** or 2–10 named choices;
`unknown` is always added as a no-action answer. At most five enabled question
automations may exist in one filing system.

Question automations use only state available after extraction: title/content
regular expressions plus existing tag and correspondent filters. Intake-only
path, filename and mail-envelope filters are rejected. Matching is recomputed
for each eligible classifier job, including an explicit LLM rescan. Refile and
`document_updated` events do not invoke the question branch.

Each action names the answer that activates it. Supported effects are adding
existing tags, assigning one existing correspondent or filing category, and
setting a fixed typed custom-field value. Document-link custom fields are not
available. Destinations and fixed values remain in Suchi; the model receives
only the automation ID, question text, and allowed answers. It cannot choose an
action, metadata ID, or arbitrary value.

### Example: warranty proof

Ask whether warranty language constitutes proof, then set an existing boolean
field and add an existing tag. If `Warranty proof` already has a value, Suchi
preserves it and can still apply the independent tag.

```json
{
  "name": "Warranty proof",
  "enabled": true,
  "triggers": [
    {
      "type": 2,
      "filter_content_matching": "warranty|guarantee"
    }
  ],
  "ask": {
    "question": "Is this valid warranty proof?",
    "answer": { "type": "yes_no" }
  },
  "actions": [
    {
      "type": "assign_tags",
      "when": "yes",
      "params": { "tag_ids": [7] }
    },
    {
      "type": "assign_custom_field",
      "when": "yes",
      "params": { "field_id": 12, "value": true }
    }
  ]
}
```

### Example: tax document type

A multiple-choice branch can file an invoice or mark a credit note without
letting the model invent a category or tag. Category assignment applies only
while the document is in Inbox.

```json
{
  "name": "Classify tax documents",
  "enabled": true,
  "triggers": [
    {
      "type": 2,
      "filter_content_matching": "invoice|credit note|tax"
    }
  ],
  "ask": {
    "question": "What kind of tax document is this?",
    "answer": {
      "type": "choice",
      "choices": ["Tax invoice", "Credit note", "Other"]
    }
  },
  "actions": [
    {
      "type": "assign_jd_category",
      "when": "Tax invoice",
      "params": { "jd_category_id": 21 }
    },
    {
      "type": "assign_tags",
      "when": "Credit note",
      "params": { "tag_ids": [13] }
    }
  ]
}
```

### Example: contract renewal clause

Use a narrow content filter so only likely contracts receive the question.
The `yes` branch records a fixed flag and review tag; `no` and `unknown` leave
the document unchanged.

```json
{
  "name": "Flag automatic renewals",
  "enabled": true,
  "triggers": [
    {
      "type": 2,
      "filter_content_matching": "renew|extension|term"
    }
  ],
  "ask": {
    "question": "Does this contract say that it renews automatically?",
    "answer": { "type": "yes_no" }
  },
  "actions": [
    {
      "type": "assign_custom_field",
      "when": "yes",
      "params": { "field_id": 44, "value": true }
    },
    {
      "type": "assign_tags",
      "when": "yes",
      "params": { "tag_ids": [19] }
    }
  ]
}
```

These IDs are examples. The visual builder uses names and saves the IDs of
destinations that already exist in the current filing system.

All matching questions share the classifier's existing single request. Each
returned answer must use an offered ID and answer, contain a confidence from
zero to one, and—except for `unknown`—include a short exact quote from the
document. Duplicate IDs, invented answers, and ungrounded evidence are ignored.
Question definitions and their ordered match set are compared again in the final
write transaction; if that set changed during the provider call, every question
answer from the call is discarded while ordinary classifier output may still
apply.

Answer actions use the same confidence threshold and automatic/review-first
setting as ordinary classifier metadata. A review card names the automation and
the proposed fixed effect. Suchi does not retain the question, raw answer, or
evidence quote as ask history; normal audit and approval records retain only
bounded automation attribution and metadata-change provenance.

## Classification order

For a newly extracted document Suchi runs:

1. local archive matching, when enabled
2. ordinary user automations in configured order
3. the optional LLM classifier, including questions from matching ask
   automations

Archive matching uses authorized lexical neighbours. With the shared automatic
application mode on (the default), eligible matches at or above `0.90` apply;
the default minimum score for review suggestions is `0.50`. Both thresholds are
configurable. Turn automatic mode off to review inferred changes before
application. Tokenization, BM25, ACLs and shared retrieval are
documented in [Search architecture: Similar documents](/search#similar-documents).

The optional model shares that mode, with a default metadata/date threshold of
`0.70`; each date uses its own score. Below-threshold changes remain suggestions.
Current source, access and field-generation checks still protect human changes
and explicit rule writes, including clears and same-value reassertions.
Classifier-owned `needs-review` markers are excluded from rule matching and
templates so a machine-created marker cannot activate a destructive rule.
Explicitly adopted or rule-assigned tags remain ordinary rule input. This does
not introduce model-authored external actions or change explicitly configured
internal automation behavior. See [LLM classifier](/llm-classifier).

## Preset ownership

Filing-tree presets seed a small starter set of automations. Editing a
preset-owned automation creates a user-owned copy and disables the original.
Reapplying a preset preserves the copy and the disabled original. Existing rule
names remain local; imports report preserved/skipped rows rather than replacing
them. The Automations screen keeps preset-owned entries in a collapsed
**Built-in automations** list so user-created rules remain easy to scan.

Taxonomy v1 imports only its explicit portable action subset, not every runtime
action. Category skips skip whole dependent starters. Default taxonomy exports
preserve supported preset-owned rule identity/order as named explicit starters,
including keyword-generated rules; disabled/unrepresentable behavior fails.
Tree-only export omits all starters. User-owned rules/forks require a complete
backup. See [Filing trees](/jd#optional-starters).

Preset category keywords match case-insensitive whole words or phrases, not
substrings: `lease` matches a lease document but not `please`. Migration `0002`
repairs existing generated preset keyword rules. User-owned copies and other
regex filters retain their explicit matching semantics. This correction does
not refile previously processed documents. Review incorrect categories before relying on archive
matching, which can otherwise reuse those documents as examples.

## API

Automations use `/api/automations/`; updates replace supplied trigger and
action arrays wholesale. Writes require administrator access. Complete
payload and error contracts live in [API](/api).

Every successful metadata mutation is audited. Failures include the document
and action kind in structured logs without document content.

## Compiled actions

`core/automations.ActionDefinition` pairs a unique `Kind`, `Validate` callback and
`Execute` callback. `NewRegistry` copies definitions into an immutable instance;
there is no default registry or runtime registration method. Assembly explicitly
combines `BuiltinActions()` with `app.Options.Actions`, then passes the same
registry to rule storage, API document updates, ingestion and refiles. Standalone
callers must supply their registry too; unknown kinds retain `unsupported kind`
errors. The existing builder schema continues to advertise the community visual
builder's subset; compiled actions can be configured through the JSON API.

`Validate(ctx, tx, systemID, params)` reads configuration/references in the
caller's transaction, both on save and immediately before execution.
`Execute(ctx, tx, ActionTarget{DocID, SystemID}, params)` receives the current
live document's system and the same writer transaction as every action in that
rule. Only the built-in idempotent discard may revisit Trash. A failure rolls
back the entire rule, including extension state and enqueued jobs. Preserve
idempotence with domain constraints/receipts because jobs and refiles can retry.
Callbacks must be concurrency-safe, and validation must only read. Do not commit
or roll back the supplied transaction, re-enter the writer, or call network or
subprocess services while holding it.

Callbacks are trusted code compiled by the distribution, not scripts supplied by
an API user. Rule CRUD still requires the existing administrator boundary;
document admission, system ownership, ACLs, approvals and audit remain Suchi's
responsibility. A target is not a principal or permission to operate on other
documents. New actions must validate their references within that system and
preserve the callers' authority. This registry does not add inferred actions,
external workers, or a new approval path. See [Plugins](/plugins#application-assembly).

## Current limits

- Filters are structural plus title/content regexes, not an arbitrary
  expression language.
- There are no scheduled triggers or built-in user-notification actions.
- Runtime scripts cannot be installed as actions; additional handlers require
  a compiled distribution.
