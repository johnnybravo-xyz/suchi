title: "Wishlist — Gmail OAuth 2.0 device-code flow"

---

Today Gmail is supported via **App Passwords** — the operator turns
on 2FA, generates a 16-char password in Google account settings, and
enters `imap.gmail.com:993` + that password into the email-accounts
form. The full-imap-support branch treats it as `auth_method:
"password"` with no special path.

That works, but it has real friction:

- App Passwords only exist when the account has 2FA on and no
  Workspace-managed password policy blocking them.
- Google is phasing App Passwords out for Workspace tenants; several
  admins now disable them entirely.
- Rotation is manual, and a leaked password gives full mailbox
  access with no scope narrowing.

The long-term fix is the same shape suchi already ships for
Microsoft: an OAuth device-code flow that hands back a refresh
token, cached under AEAD, refreshed silently on boot.

Status: **wishlist**. No code. This doc is what the future PR lands
against.

## Scope

Add `core/ingest/emailwatch/oauth/google.go` mirroring
`core/ingest/emailwatch/oauth/microsoft.go`. Reuse the same call
sites — `oauth.AcquireToken`, `oauth.AcquireTokenSilent`, and the
XOAUTH2 SASL handshake at
`core/ingest/emailwatch/oauth/xoauth2.go` — so the Watcher stays
provider-agnostic. `emailaccounts.Provider = "gmail"` starts
selecting the new module when `AuthMethod = "oauth"`.

## Design

### 1. Endpoints + scopes

- Device authorization: `https://oauth2.googleapis.com/device/code`
- Token exchange: `https://oauth2.googleapis.com/token`
- Scope: `https://mail.google.com/` (Gmail IMAP access — Google
  scopes IMAP under this single URL, not a granular pair like
  Microsoft's `IMAP.AccessAsUser.All` + `offline_access`).
- No separate `offline_access` scope — Google returns a refresh
  token whenever `access_type=offline` is passed in the initial
  device-code request.

### 2. Client credentials

Google requires an OAuth client id even for device-code flows.
Options:

- **Suchi-owned public client**: register a project in Google
  Cloud, get a client id, ship it as `DefaultClientID` alongside
  `microsoft.DefaultClientID`. Requires the project to pass Google's
  **restricted-scope verification** because `https://mail.google.com/`
  is a restricted scope. That's a ~4-6 week review with a security
  assessment. Not zero-cost.
- **Per-operator client id**: each operator registers their own
  Google Cloud project and enters the client id in the account form.
  Skips verification (unverified apps work for the project's own
  test users), but requires the operator to add each Gmail address
  as a test user manually and the resulting consent screen shows an
  "unverified app" warning until it hits the 100-user cap.
- **BYO client id via env**, same shape as `INGEST_IMAP_OAUTH_CLIENT_ID_MICROSOFT`:
  operator sets `INGEST_IMAP_OAUTH_CLIENT_ID_GOOGLE` and points at
  their own Google Cloud project. This is the pragmatic first
  landing — it defers the verification question without blocking
  advanced users.

Recommendation: land the module with BYO client id first. Suchi-
owned verified client id is a follow-up once real usage justifies
the review overhead.

### 3. Token cache shape

Google's refresh tokens are opaque strings, not MSAL-shaped account
graphs. The persisted blob is simpler than the Microsoft cache — a
JSON object with `refresh_token`, `access_token`, `expires_at`,
`token_type`. Reuse `core/crypto.AEADKey` to seal it into
`emailaccounts.oauth_cache` the same way the Microsoft cache is
stored. `oauth.ErrCacheStale` semantics carry over — refresh
failure surfaces to the operator via the same "reconnect" flow.

### 4. XOAUTH2 wire format

Identical to Microsoft — `base64("user=" + email + "^Aauth=Bearer "

- token + "^A^A")`where`^A`is`\x01`. The existing helper at
`oauth/xoauth2.go` is provider-neutral and gets reused unchanged.

### 5. UI

`ui/src/lib/MailAccountForm.svelte` already knows about the Gmail
preset. The follow-up change: when `provider = "gmail"` AND
`auth_method = "oauth"`, swap the password field for the same
device-code modal `MailAccountForm.svelte` already renders for
Microsoft. No new component.

## Verification (future PR)

- Unit tests mirror `oauth/microsoft_test.go`: happy-path device
  code, refresh, cache-stale error path.
- Integration test against a throwaway `@gmail.com` account:
  device-code round trip, single-message fetch, refresh across a
  process restart.
- Docs update in `docs/config.mdx` documenting
  `INGEST_IMAP_OAUTH_CLIENT_ID_GOOGLE` and the (unverified-app)
  operator setup checklist.

## Not doing

- **Service accounts / domain-wide delegation** — that's the
  Workspace admin path, orthogonal to per-user consent. Separate
  wishlist entry when there's demand.
- **Fallback to per-account username/password after OAuth fails** —
  auth mode is chosen at account-creation time; forcing a swap
  invites confusion. Operator can re-create the account if they
  need to change mode.
- **Google account chooser inside the SPA** — device code is
  copy-paste-to-browser by design; embedding a chooser adds a
  Google-SDK dependency the rest of the codebase doesn't need.
