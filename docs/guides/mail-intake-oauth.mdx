---
title: "Sign in to Microsoft / Outlook"
description: "OAuth2 device-code flow for Microsoft-hosted mailboxes."
---

Microsoft is retiring basic authentication for IMAP on both personal
Microsoft accounts and Microsoft 365 tenants. If you try to sign in
with a password today, the IMAP server answers `LOGIN failed: Login
is disabled in current state`. OAuth is the only working path — and
the only auth mode suchi offers for the `microsoft` provider preset.

Suchi uses the OAuth 2.0 **device code** flow. The sign-in happens in
your browser on any device; the suchi server never sees your Microsoft
password. What it stores is an opaque, sealed MSAL token cache that
gets refreshed silently on every poll.

## What you'll need

- A Microsoft account (personal `@outlook.com` / `@hotmail.com`, or a
  work / school account).
- A browser on any device. It does not have to be the same machine
  the suchi server runs on — the phone in your pocket is fine.
- The suchi Admin UI open in a tab.

## Walkthrough

1. In **Admin → Mail intake**, click **Add mailbox** and pick
   **Microsoft** in the provider dropdown. Host, port, TLS, and
   auth method auto-fill.
2. Fill in the display **Name**, choose an **Owner** user, and
   enter your Microsoft address as the **Username**.
3. Click **Sign in with Microsoft**. Suchi calls
   `POST /api/admin/email-accounts/oauth/start` and opens a modal.
4. The modal shows an 8- or 9-character **user code** and the URL
   `https://microsoft.com/devicelogin`. Open the URL in any browser,
   paste the user code, and press Next.
5. Microsoft shows an OAuth consent screen: "suchi wants to access
   your mailboxes as you" (or your Azure app registration's display
   name if you brought your own). Approve it.
6. The suchi modal closes automatically as soon as the device-code
   flow completes on Microsoft's side. The row header now reads
   "Signed in as `your.address@example.com`".
7. Save the row, then click **Test connection**. Suchi refreshes
   the token, dials `outlook.office365.com:993`, authenticates with
   `AUTHENTICATE XOAUTH2`, and logs out. A green "Connected —
   mailbox reachable" confirms the whole loop works.

If the code expires before you approve (5-minute TTL), just click
**Sign in with Microsoft** again for a fresh one.

## What the flow stores

The suchi server stores a **sealed MSAL cache** in the row's
`sealed_secret` column: an opaque blob containing the access token,
refresh token, and account metadata that MSAL-Go needs to renew.
The blob is encrypted at rest with the same AEAD key
(`$DATA_DIR/.decrypt-key`) that seals every other secret in the
database. Nothing about the token is human-readable in the DB.

On every poll, suchi asks MSAL to `AcquireTokenSilent` against the
sealed cache. That call either returns a fresh access token from
the in-memory cache or hits Microsoft's refresh endpoint. Either
way, the updated cache is re-sealed and written back to the row.

If refresh fails — for example, you revoked the app in Microsoft's
dashboard, or the tenant admin invalidated the consent — the row's
`last_error` shows the MSAL diagnostic verbatim, and
**Test connection** returns the same error. Fix it by revoking the
row (below) and signing in again from scratch.

## For Entra tenant admins (optional)

**Skip this whole section if you're using suchi personally.** The
default `Suchi - Microsoft OAuth` app the project ships with handles
sign-in for personal Microsoft accounts, free Outlook.com, Hotmail,
and small tenants out of the box — no Azure work on your side.

Register your own Entra app instead of using the default only when:

- **Tenant scoping.** Your Entra tenant admin can grant admin
  consent to your app registration once, so users in the tenant
  never see the Microsoft consent prompt individually.
- **Trust display.** The Microsoft consent screen shows the app
  name registered in Azure. Users are more likely to approve a
  prompt from `Suchi - Acme` than from the ships-in-the-box
  default.

### Register the Azure app

One-time checklist under your own tenant.

1. Sign in to <https://portal.azure.com> → **Microsoft Entra ID** →
   **App registrations** → **New registration**.
2. **Name**: `Suchi - <your deployment nickname>` — e.g.
   `Suchi - Acme` or `Suchi - Home`. Every operator-visible
   identifier suchi emits to external systems uses the
   `Suchi - <nickname>` shape (source of truth:
   `plugin-api.BrandPrefix`, referenced by `DefaultAppName` in
   `core/ingest/emailwatch/oauth/microsoft.go`) so a tenant admin
   auditing OAuth grants can grep one predictable prefix to spot
   every suchi-owned entry across their console.
3. **Supported account types**: **Accounts in any organizational
   directory (any Microsoft Entra ID tenant — Multitenant) and
   personal Microsoft accounts (e.g., Skype, Xbox)**. This is the
   `AzureADandPersonalMicrosoftAccount` audience. Anything narrower
   locks out personal `@outlook.com` / `@hotmail.com` users.
4. **Redirect URI**: leave empty. Device-code flow is a public
   client and does not use a redirect.
5. Click **Register**.
6. In the new app: **Authentication** → **Advanced settings** →
   **Allow public client flows** → **Yes** → **Save**. Without
   this, MSAL device-code returns
   `AADSTS7000218: The request body must contain the following
parameter: 'client_assertion' or 'client_secret'`.
7. **API permissions** → **Add a permission**. Do **not** pick
   Microsoft Graph — Graph's IMAP scope does not authorize
   `outlook.office365.com` IMAP. Instead choose **APIs my
   organization uses**, search for **Office 365 Exchange Online**,
   pick it, then **Delegated permissions** → check
   **IMAP.AccessAsUser.All** → **Add permissions**.
8. Same **Add a permission** flow: **Microsoft Graph** →
   **Delegated permissions** → check **offline_access** → add.
   This is what lets MSAL refresh silently on every poll instead
   of prompting the user every hour.
9. (Optional, tenant deployments only.) Click **Grant admin
   consent for <tenant>**. Personal-account users don't need this
   — they'll consent individually when they hit the device-code
   screen — but granting it once suppresses the prompt for every
   user in your tenant.
10. Back on the app's **Overview** page, copy the **Application
    (client) ID** GUID.

The client ID is a public identifier, not a secret — device-code
flow never uses a client secret.

### Point suchi at your app

1. Set `INGEST_IMAP_OAUTH_CLIENT_ID_MICROSOFT=<your-client-id>`
   in the suchi environment and restart. New OAuth flows now
   run against your app registration. Rows already signed in
   with the default app keep working until their refresh token
   expires (typically 90 days).
2. (Maintainer-only.) If you're updating the project-shipped
   default, paste the new GUID into
   `core/ingest/emailwatch/oauth/microsoft.go` as the value of
   `DefaultClientID`. The `DefaultAppName` constant right below
   composes the display name from `pluginapi.BrandPrefix` — leave
   it as-is unless you're also changing the nickname.

## Revoking access

To sign a row out from suchi:

1. Open **Admin → Mail intake** and click **Edit** on the row.
2. Click **Revoke sign-in**. Suchi calls
   `POST /api/admin/email-accounts/{id}/oauth/revoke`, clears
   `sealed_secret`, sets `enabled=false`, and flips
   `auth_method` back to `password`.
3. This only invalidates the token **on suchi's side**. To
   invalidate Microsoft-side (so the refresh token can't be
   re-used elsewhere), visit
   [mysignins.microsoft.com/security-info](https://mysignins.microsoft.com/security-info)
   and remove the `Suchi - <nickname>` entry from the list of
   signed-in apps.

Do both if you're rotating for a credential-leak scare — clearing
`sealed_secret` alone leaves the refresh token valid upstream.
